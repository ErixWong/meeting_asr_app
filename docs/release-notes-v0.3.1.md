## 二、录音保护（issue #74 收尾）

### 1. `connecting` 期间取消不再漏掉第二路采集

**问题**：`startRecording` 按设备逐路 `await` 启动，循环里没有取消检查。双路输入时，
第一路还在等权限/握手，用户就离开或点「新建会议」——取消只停掉已存在的那一路并替换 ref，
循环继续启动第二路，而它已不在 ref 里，**再也停不掉**：麦克风继续采、音频继续写。

**修法**：用「Map 身份」判定本轮启动是否作废（所有取消路径都是把 ref 换成新 Map，
所以身份比较自动覆盖将来新增的取消路径），循环里两处检查：每轮开头、`await` 返回之后。

### 2. 离页保护补齐（idle 状态不再丢转写）

**问题**：保存失败时 `status` 回到 `idle` 但转写仍在内存；而 `/chat` 链接只在 `recording/paused`
时拦截，顶栏「⚙ 管理」完全没有拦截，`beforeunload` 又只管整页卸载。⇒ 点顶栏就把转写丢了。

**修法**：新增模块级「有未保存工作」标志，顶栏与 `/chat` 链接都接上确认框；首页卸载时清零。

### 3. 保存重试加幂等键（只覆盖 POST 建会议）

**问题**：`requestJson` 是裸 `await fetch`（无超时），服务端 `createMeeting` 不去重。
「服务端已提交但响应丢了」时点「重试保存」会**多出一条会议**。

**修法**：

- 迁移 v6 新建 `idempotency_keys`；**写入前原子认领**，完成动作在**业务事务内部**
- 认领带**持有者令牌**，`complete` / `release` / TTL 回收都校验令牌，旧持有者无法影响新认领者
- 幂等命中时**不再触发 LLM 生成**（否则重试会给同一会议再跑一次纪要）
- 覆盖三条 POST：主保存、ASR checkpoint（新录音时作废旧键）、文件上传（**不做**，见下）

**未覆盖（已知限制）**：

| 路径 | 为什么不做 |
|---|---|
| `PATCH /api/meetings/:id` 追加转写 | 副作用分散在四个独立事务里（追加/标题/状态/LLM 触发），一个幂等键无法原子覆盖。半吊子实现只能在「重试跳过遗漏副作用」和「重复追加」之间二选一。**后果**：PATCH 响应丢失后重试会重复追加同一段转写（用户可见、可删会议清理） |
| 文件上传 | 没有重试入口；用文件身份派生确定性键会让「有意重复上传同一文件」被误去重；文件名拼接会超出 `key` 列的 128 字符上限 |

## 三、顺带修掉的两个真实缺陷

### `crypto.randomUUID()` 在非安全上下文不可用（P0）

开发幂等键时用了 `crypto.randomUUID()`，它**只在安全上下文**（HTTPS / `http://localhost`）可用。
本应用按 `http://<内网IP>:3123` 部署，那里它是 `undefined` —— **每次保存都会抛错**。

改为三级降级：`randomUUID` → `getRandomValues`（不受安全上下文限制）→ 时间戳+随机兜底。

### `key` 是 MySQL / SQL Server 保留字

`idempotency_keys.key` 在查询里必须按方言加标识符引号（sqlite `"x"` / mysql `` `x` `` / mssql `[x]`），
沿用 `server/db/insert-ignore.mjs` 的同一套映射。
