# 260724 Improve - Backend Runtime Design

## 1. 目标

明确系统运行时架构、配置读取路径、代理职责、数据库生效机制以及关键失败处理方式，避免后续实现中出现多套真相源和配置修改不生效的问题。

## 2. 运行时架构目标

当前系统未来应形成以下运行结构：

1. 浏览器前端
   负责录音、上传、纪要查看、编辑、重解析、发邮件。
2. Next.js 应用层
   负责页面渲染、API、数据库读写、LLM 调用、邮件发送。
3. 本地 ASR 代理层
   负责浏览器音频流接入、协议兼容、转发到 DashScope 或本地 FunASR。
4. SQLite 数据库
   负责配置、会议、纪要、邮件记录、审计等持久化。

## 3. 为什么需要单独定义运行时设计

目前文档已经提出：

1. 不再依赖 `.env.local` 作为运行期配置源。
2. 管理页面保存的配置要立即影响录音、纪要生成和邮件发送。
3. 代理层和 Next API 都要读同一套配置。

如果不提前定义运行时读取方式，会产生以下问题：

1. 页面保存了配置，但代理仍然使用旧配置。
2. Next API 与代理各自维护一套缓存。
3. 配置热更新行为不一致。
4. 问题排查时无法确认当前生效的是哪套配置。

## 4. 建议运行时组件职责

### 浏览器前端

职责：

1. 采集麦克风或 USB 设备音频。
2. 连接固定本地 WebSocket 入口。
3. 展示实时转写结果。
4. 调用会议保存、纪要重解析、邮件发送等 API。

不负责：

1. 保存系统级配置。
2. 直接连接第三方 ASR / LLM。
3. 直接写原始业务数据到本地文件。

### Next.js API 层

职责：

1. 统一作为业务 API 入口。
2. 统一读写 SQLite。
3. 读取当前激活配置。
4. 调用 OpenAI 兼容 LLM。
5. 调用邮件发送服务。
6. 记录会议、纪要、发送记录和审计日志。

### ASR 代理层

职责：

1. 暴露固定 WebSocket 地址给浏览器，例如 `ws://host:8080`。
2. 根据当前激活 ASR 配置，连接 DashScope 或本地 FunASR。
3. 做协议兼容和消息翻译。
4. 可选记录原始 ASR 事件集合。

不负责：

1. 管理界面。
2. LLM 调用。
3. 邮件发送。

## 5. 配置真相源建议

建议将 SQLite 作为唯一运行期真相源。

具体原则：

1. `.env.local` 只用于开发期启动参数或极少数底层基础变量。
2. ASR / LLM / Mail 等系统配置全部存数据库，模板定义和热词表存独立业务表。
3. 前端、Next API、代理都只认数据库中的当前设置项。

### 关于配置组织方式的建议

建议将系统配置统一收敛到 `app_settings`：

1. 以 `item_section` 区分 `asr`、`llm`、`mail`、`system`。
2. 以 `item_mark` 表示字段语义，例如 `provider`、`base_url`、`api_key`、`default_prompt_template_id`。
3. 以 `item_value` 保存实际值，复杂结构允许 JSON。

不再建议单独维护 `asr_endpoints`、`llm_endpoints`、`mail_settings` 这类配置表。

原因：

1. 当前系统一期本质上只需要“当前生效设置”，而不是复杂配置中心。
2. 配置页保存逻辑会明显更简单。
3. 排查问题时可以直接查看 `section + mark + value`。

这意味着：

1. `app_settings` 本身同时表达“配置项是什么”和“当前值是什么”。
2. LLM 清洗模板不放进 `app_settings`，而是存到 `llm_prompt_templates`。
3. ASR 热词不放进 `app_settings`，而是存到 `asr_hotwords`。
4. 默认模板由 `system.default_prompt_template_id` 这样的设置项表达。

## 6. 配置生效机制建议

这是当前最关键的运行时设计点。

### 6.0 `base_url` 统一语义

为避免不同文档和实现对 `base_url` 的理解不一致，统一规定：

1. `base_url` 永远表示“用户填写的服务根地址”。
2. `base_url` 不直接表示最终动作路径。
3. 最终运行时目标由服务端根据 provider 类型派生。

具体到不同能力：

1. `asr.endpoint`
   用户可填写 `http://host:10095` 或 `ws://host:10095/ws`，运行时统一规范化为真正的 WebSocket 目标。
2. `asr.workspace_id`
   仅 DashScope 模式使用，运行时目标可由 `workspace_id` 派生。
3. `llm.base_url`
   用户填写如 `http://host:port/v1`，运行时再补 OpenAI 兼容动作路径。

### 6.1 Next API 生效机制

Next API 每次处理请求时，都从数据库读取当前激活配置，或读取一个短时缓存。

一期建议：

1. 配置量很小。
2. 先直接每次请求读取数据库。
3. 如后续有性能问题，再引入只读短缓存。

优点：

1. 实现简单。
2. 配置保存后立即生效。
3. 不需要复杂刷新机制。

### 6.2 代理层生效机制

代理层必须明确当前 ASR 配置的读取时机。

建议一期采用：

1. 代理进程常驻。
2. 每次有新的浏览器 WebSocket 连接建立时，代理从数据库读取 `app_settings` 中 `asr` 分组配置，并读取 `asr_hotwords` 中 `status = active` 的热词。
3. 代理在首帧初始化 JSON 中，将热词表转成 `hotwords` JSON 字符串传给 FunASR。
4. 该连接生命周期内固定使用这套配置和热词。
5. 后续管理页面修改配置或热词，只影响新建连接，不强行切换当前已在录音中的连接。

说明：

1. 这里的 `hotwords` 传输格式应遵循 [hotwords-howto.md](./hotwords-howto.md) 中的首帧 JSON 方案。

这是当前最稳妥的方式，原因：

1. 不需要热切换正在进行中的上游 ASR 连接。
2. 用户认知清晰：改配置后“下一次录音”生效。
3. 实现复杂度远低于连接内动态切换。

### 6.3 页面文案建议

后台保存配置后，建议提示：

- 新配置会对后续新建录音连接、纪要生成和邮件发送生效。
- 当前进行中的录音不会被中断或热切换。

## 7. 原始 ASR 结果保存责任建议

当前需要解决“原始 ASR 结果到底由谁保存”的问题。

建议一期采用：

1. 代理层负责在单次连接生命周期内采集原始上游消息。
2. 代理为每次录音或上传识别生成一个 `capture_session_id`。
3. 代理把原始事件集合暂存为短生命周期采集产物。
4. 浏览器在调用 `POST /api/meetings` 时只提交 `captureSessionId` 和规范化分段。
5. Next API 根据 `captureSessionId` 读取代理侧采集产物，并负责最终落库到 `meeting_asr_results`。

原因：

1. 浏览器当前拿到的是较简化结果，不足以完整保留原始事件。
2. 原始上游消息最接近代理层，采集成本最低。
3. 浏览器不应承担搬运大块基础设施原始 payload 的职责。
4. 业务落库仍交给 Next API，避免代理直接承担复杂数据库事务。

可替代方案：

1. 代理直接写数据库。

但一期不建议这样做，原因：

1. 代理职责会过重。
2. 数据库写入逻辑分散到两个运行组件中。
3. 出错后更难排查。

## 8. 会议保存与纪要生成边界

建议拆成两个明确阶段：

1. 第一步：事务内提交会议和原始 ASR 结果。
2. 第二步：事务提交成功后，再触发默认 LLM 清洗。

产品规则建议：

1. 即使 LLM 生成失败，会议和转写结果也必须保留。
2. 失败后会议进入 `llm_failed`。
3. 用户可以手动重试。

工程规则建议：

1. `POST /api/meetings` 不因为默认 LLM 清洗失败而回滚会议事实。
2. 默认 LLM 清洗可以是“提交后同步触发”或“提交后异步触发”，但都必须是 post-commit 行为。
3. 系统应允许会议处于“已保存但 LLM 清洗中/失败”的中间状态。

这比“保存会议时整单回滚”更合理。

## 9. 邮件发送运行时规则

建议邮件发送统一由 Next API 完成。

原因：

1. 邮件本质是业务动作。
2. 需要写发送记录。
3. 需要受权限控制。
4. 需要写审计日志。

不建议：

1. 浏览器直接发 SMTP。
2. 代理层发邮件。

## 10. 运行期健康检查建议

建议至少支持以下健康检查：

1. 数据库可连接。
2. 当前 `asr` 设置可连接。
3. 当前 `llm` 设置可调用。
4. 当前邮件配置可用。
5. 代理服务在线。

建议在后台提供系统状态页。

## 11. 错误处理原则

建议所有关键失败都遵循：

1. 保留已成功的上一步数据。
2. 给出明确失败原因。
3. 允许用户重试。
4. 记录审计和错误日志。

### 典型场景

#### ASR 失败

- 保留会议壳或临时记录
- 标记 `transcribe_failed`
- 允许重新录音或重新上传

#### LLM 失败

- 保留会议与转写
- 标记 `llm_failed`
- 允许重新解析

#### 邮件失败

- 保留纪要正式版本和收件人信息
- 标记 `send_failed`
- 允许修正后重发

## 12. 一期建议技术约束

1. 单机 SQLite。
2. 单个 Next 服务实例。
3. 单个代理进程实例。
4. 不做分布式队列。
5. 不做复杂配置中心。

## 13. 对数据库设计的修订建议

建议补充或调整：

1. `app_settings` 作为大多数配置的统一入口。
2. 去掉独立配置表，避免多表同步与双真相源。
3. `meeting_asr_results` 增加 ASR 配置快照字段。
4. `meetings` 增加 `status`、`last_error_message`。
5. 邮件配置和发送记录入库。

## 14. 对 API 设计的修订建议

建议补充或调整：

1. 配置保存后说明“对新连接生效”。
2. `POST /api/meetings` 只保证会议保存，不把 LLM 成败作为整体事务回滚条件。
3. 增加后台系统状态接口。
4. 增加邮件配置接口和测试接口。
