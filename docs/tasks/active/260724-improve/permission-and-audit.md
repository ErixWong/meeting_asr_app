# 260724 Improve - Permission and Audit Design

## 1. 目标

为企业内网会议纪要系统定义最小可用的权限模型和审计模型，支撑后续域账号自动登录接入、会议可见范围控制和敏感操作追踪。

## 2. 设计背景

当前系统计划部署在企业内网，并在后续接入域账号自动登录。即使登录接入延后，权限边界和审计模型也不应等到最后再补。

原因：

1. 会议纪要涉及敏感业务信息。
2. 邮件发送属于正式对外或对内分发动作。
3. 声纹样本属于敏感数据。
4. 管理后台配置变更会直接影响系统行为。

## 3. 一期设计原则

1. 先按单租户企业内部系统设计。
2. 用户身份可先抽象，不要求当前阶段就完成域账号接入。
3. 即使暂未接入 SSO，也应预留 `user_id`、`account_name`、`display_name` 等字段。
4. 审计优先记录“谁做了什么”，再逐步扩展“为什么做”。

## 4. 角色建议

### `user`

普通用户。

建议能力：

1. 创建会议。
2. 开始录音、上传音频。
3. 查看自己可见的会议。
4. 生成纪要、重新解析。
5. 编辑会议纪要正式版本。
6. 发起邮件发送。

### `system_admin`

管理员，包含普通用户的业务能力。

建议能力：

1. 管理提示词模板、热词、声纹映射与样本。
2. 处理失败会议，代为发送或重发会议纪要。
3. 管理 ASR 配置、LLM 配置和邮件设置。
4. 管理用户与角色配置。
5. 查看系统状态和错误摘要。
6. 查看审计日志。

## 5. 会议可见范围建议

一期至少需要明确：

1. 会议创建人默认可见。
2. 会议组织者可见。
3. 被列为参与人或收件人的用户可见。
4. `system_admin` 默认可查看全部会议，但需要审计。

如果一期还不做精细可见范围，也建议至少预留字段和规则，不要默认所有登录用户可见全部会议。

## 6. 权限域建议

建议把权限按以下域拆分：

1. 会议管理
2. 配置管理
3. 模板管理
4. 声纹管理
5. 邮件发送
6. 审计查看
7. 系统状态查看

示例权限点：

- `meeting:create`
- `meeting:view`
- `meeting:edit`
- `meeting:send`
- `meeting:archive`
- `settings:manage_asr`
- `settings:manage_llm`
- `settings:manage_mail`
- `prompt:manage`
- `speaker:manage`
- `audit:view`
- `system:view_status`

## 7. 一期实现建议

一期不必做复杂 RBAC 引擎，但建议在设计上预留：

1. 用户表。
2. 角色表。
3. 用户角色映射。
4. 会议可见范围字段或关联表。

如果当前阶段还没有真实登录，可先：

1. 在文档和数据库中预留字段。
2. API 层允许临时使用开发身份。
3. 等域账号接入后替换身份来源。

## 8. 审计对象建议

以下操作建议强制审计：

1. 创建会议。
2. 删除会议。
3. 修改会议标题。
4. 触发默认纪要生成。
5. 手动重解析纪要。
6. 设定当前正式纪要版本。
7. 发起邮件发送。
8. 重发邮件。
9. 修改 ASR 配置。
10. 修改 LLM 配置。
11. 修改提示词模板。
12. 修改邮件设置。
13. 录入、修改、删除声纹样本。
14. 查看敏感后台页面。

## 9. 审计日志建议字段

建议增加 `audit_logs` 表。

建议字段：

- `id`
- `actor_user_id`
- `actor_account_name`
- `actor_display_name`
- `action_type`
- `resource_type`
- `resource_id`
- `resource_name`
- `request_id`
- `ip_address`
- `user_agent`
- `before_snapshot`
- `after_snapshot`
- `result`
- `error_message`
- `created_at`

说明：

1. 配置变更、模板变更、权限变更建议保留 before/after。
2. 会议发送类动作至少要记录结果与错误信息。

## 10. 声纹相关权限建议

声纹数据应视为敏感数据，建议规则：

1. 只有 `system_admin` 可以管理。
2. 普通用户不可查看样本音频。
3. 删除样本必须写审计日志。
4. 下载或导出样本如后续开放，也必须单独授权。

## 11. 邮件发送相关权限建议

建议区分：

1. `meeting:send`
   允许发送纪要邮件。
2. `settings:manage_mail`
   允许修改 SMTP 或邮件配置。
3. `audit:view`
   允许查看发送历史和失败原因。

对于外部邮箱发送，建议后续可扩展控制策略：

1. 禁止发送到企业外域名。
2. 允许白名单域名。
3. 需要管理员额外审批。

## 12. 后续域账号接入建议

等到后续接入企业域账号时，建议：

1. 将域账号唯一标识映射到 `account_name` 或 `external_user_id`。
2. 登录成功后同步用户基础信息。
3. 角色仍由本系统维护，不直接完全依赖 AD 组，除非后续明确需要。

这样可以降低一期复杂度，同时保留接入空间。

## 13. 后台页面建议

后台建议增加：

1. 用户与角色页。
2. 审计日志页。
3. 系统敏感操作查看页。

一期如果不立即做完整 UI，也建议先在数据和 API 设计中预留。

## 14. 与数据库和 API 的关系

### 数据库建议补充

建议增加：

1. `users`
2. `roles`
3. `user_roles`
4. `meeting_participants`
5. `audit_logs`

### API 建议补充

建议后续增加：

1. `GET /api/admin/users`
2. `GET /api/admin/roles`
3. `POST /api/admin/users/:id/roles`
4. `GET /api/admin/audit-logs`
5. `GET /api/admin/audit-logs/:id`

## 15. 一期边界

一期建议不做：

1. 复杂组织架构同步。
2. 动态策略引擎。
3. 行级非常细粒度的自定义授权规则。
4. 外部审批工作流。
