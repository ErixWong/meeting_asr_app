# 260724 Improve - Product Improvement Plan

## 1. 目标定位

当前系统需要从“录音转写原型”升级为“企业内部专业会议纪要系统”。

预期使用方式：

1. 在企业内网部署并访问。
2. 用户使用本机麦克风或 USB 设备采集会议音频。
3. 系统完成 ASR 转写。
4. 系统调用 LLM 按不同模板生成会议结果。
5. 用户确认结果内容与收件人后，通过邮件发送会议结果。
6. 管理员在后台维护系统配置、模板和热词表。

## 2. 产品演进目标

系统不应只停留在“把语音转成文本”，而应形成完整的会议处理闭环：

1. 会前准备
2. 会中采集
3. 会后整理
4. 审核确认
5. 邮件分发
6. 历史追溯
7. 后台管理

## 3. 当前新增范围

基于现阶段讨论，产品改进计划新增以下方向：

1. 支持企业内网部署场景。
2. 支持用户使用本机麦克风和 USB 设备采集音频。
3. 支持 ASR 完成后自动调用 LLM 清洗文本。
4. 支持按不同模板重新解析会议结果。
5. 支持填写收件人邮箱并发送会议结果邮件。
6. 管理员页面升级为独立后台页面，而不是 modal。
7. 后台增加热词表管理页面或分区。
8. 后台增加邮件发送配置页面。
9. 后续接入域账号自动登录和权限体系。

## 4. 产品视角下缺失的核心能力

### 4.1 会议主流程闭环

当前设计主链路是“录音 -> 转写 -> LLM -> 发邮件”，但还缺完整的产品闭环。

建议补齐：

1. 会前：新建会议、录入标题、选择默认模板。
2. 会中：展示录音状态、设备状态、ASR 状态、网络状态。
3. 会后：自动生成首版结果、人工校对、重新解析、确认收件人、发送邮件。

建议原则：

1. 默认自动生成结果。
2. 默认不自动发邮件，先由用户确认后发送。
3. 自动发送作为后续高级能力，而不是一期默认行为。

### 4.2 结果编辑与版本管理

会议结果应视为正式业务文档，而不是一次性 LLM 输出。

建议补齐：

1. 结果编辑器。
2. 结果版本管理。
3. 当前选中版本展示。
4. 发布前预览。

建议至少区分以下层级：

1. 原始 ASR 文本。
2. LLM 首版结果。
3. 手动重解析版本。
4. 用户确认后发送的最终版本。

### 4.3 邮件分发能力

邮件发送不能只停留在一个“输入邮箱并发送”的按钮。

建议补齐：

1. 收件人类型：主送、抄送。
2. 收件人来源：手工输入、历史复用。
3. 邮件模板类型：正式纪要、简版同步、决策确认、行动项跟进。
4. 发送记录：发件人、时间、对象、结果、失败原因。

### 4.4 管理后台信息架构

管理员页面应从当前原型升级为独立后台，而不是 modal。

建议至少包含以下分区：

1. ASR 配置。
2. LLM 配置。
3. 邮件配置。
4. 提示词模板管理。
5. 热词表管理。
6. 用户与权限。
7. 系统运行状态。

### 4.5 会议对象模型

系统需要正式定义“会议”对象，而不只是转写结果集合。

一条会议建议至少包含：

1. 基本信息：标题、时间、时长、创建人。
2. 内容信息：原始 ASR、LLM 结果版本。
3. 分发信息：邮件发送记录、发送状态。
4. 生命周期状态。

### 4.6 生命周期状态机

建议尽早设计会议状态机，否则列表、筛选、发送、重解析会变乱。

建议初始状态：

1. `draft`
2. `recording`
3. `transcribed`
4. `llm_processing`
5. `pending_review`
6. `sent`
7. `archived`
8. `llm_failed`
9. `send_failed`

### 4.7 异常场景设计

企业场景下必须设计失败路径。

至少需要覆盖：

1. 麦克风权限失败。
2. USB 设备断开。
3. ASR 连接中断。
4. 录音过程中页面关闭或异常退出。
5. LLM 生成失败。
6. 邮件发送失败。
7. 邮箱格式错误。
8. SMTP 配置错误。

### 4.8 权限、审计与合规

因为系统运行在企业内网，权限和审计不可后补。

建议补齐：

1. 角色划分：普通用户、纪要管理员、系统管理员。
2. 会议可见范围：谁能看谁的会议。
3. 操作审计：谁生成、谁编辑、谁发送、谁删除。
4. 敏感信息处理：是否支持脱敏。
5. 外部邮箱发送控制。

### 4.9 搜索、归档与统计

专业系统需要能管理历史沉淀。

建议补齐：

1. 历史会议搜索。
2. 多维筛选：时间、创建人、模板、发送状态。
3. 归档能力。
4. 统计能力：会议数量、模板使用率、发送成功率、识别失败率。

### 4.10 行动项结构化

会议系统的进一步价值，在于把行动项从文本里抽出来。

建议一期先支持：

1. 从结果中提取行动项。
2. 人工确认负责人和截止时间。
3. 在会议详情页展示任务列表。

### 4.11 运维与可观测性

内网系统也需要可维护。

建议补齐：

1. 健康检查页面。
2. ASR / LLM / 邮件连通性测试。
3. 配置变更记录。
4. 错误日志摘要。
5. 当前版本信息。
6. 代理服务状态。

## 5. 建议的信息架构

建议产品页面结构至少为：

1. 会议主页
   负责录音、上传、快速进入最新会议。
2. 会议详情页
   负责原始 ASR、结果版本、重解析、发送邮件、发送记录。
3. 历史会议页
   负责搜索、筛选、归档、再次发送。
4. 管理后台
   负责 ASR、LLM、邮件、模板、热词、权限、系统状态。
5. 个人设置页
   后续可承接默认设备、默认模板、默认签名等个性化偏好。

## 6. UI 结构建议

### 6.1 会议主页

建议只承担“采集入口”和“快捷入口”职责，不再承载完整会议详情。

建议至少包含：

1. 录音控制区。
2. 设备选择区。
3. 实时转写预览区。
4. 快速进入最近会议。
5. 上传音频入口。

### 6.2 会议详情页

建议独立出来，至少包含：

1. 顶部会议基本信息。
2. 左侧结果版本列表。
3. 中间结果正文与原始转写切换。
4. 右侧操作区：重解析、收件人、发送。
5. 底部发送记录。

### 6.3 管理后台

建议使用左侧导航或顶部 tabs，而不是无限堆叠卡片。

原因：

1. 配置、模板、热词已经是三类不同数据。
2. 后续还会增加权限和系统状态。
3. 卡片堆叠会很快失控。

## 7. 优先级建议

### P0

1. 会议状态机。
2. 结果版本管理。
3. 邮件发送流程与发送记录。
4. 管理后台信息架构。
5. 热词表管理与配置生效机制。
6. 配置变更后的生效机制。
7. 权限与审计边界。
8. 异常场景与失败重试机制。

### P1

1. 历史搜索与筛选。
2. 归档与再次发送。
3. 行动项结构化。
4. 邮件模板与发送策略。
5. 通讯录或参与人带出。

### P2

1. 域账号自动登录。
2. 企业通讯录深度集成。
3. 外部任务系统对接。
4. 脱敏与更多合规策略。
5. 统计报表增强。
